# 转发消息视频下载失败分析

日期：2026-09-04  
对象：群 `663964060` 最新一条合并转发（20:18:39）  
状态：分析有效。bot 侧 B1（转发也 `get_file` + 40s 超时 + 并发）已落地，**这条 11 个视频仍全部超时**，根因是 NapCat。结论与「不要反复试错」已写入 `AGENTS.md`「转发嵌套视频」节。

---

## 1. 结论

这条转发里 **11 个视频全部失败，24 张图片全部成功**。

失败不是 HTTP 下载超时，也不是 CDN 返回 403。链路在更前面就断了：

1. **NapCat 把内层视频转成 OneBot 段时，拿不到 CDN URL**。报错是 `invalid uint 32: NaN`，随后 `video-url-get` 熔断。
2. NapCat 的失败回退把 `url` 填成了小号本地缓存路径（`2065277052\...\Video\2026-08\Ori\*.mp4`）。
3. 该路径文件 **小号没有、主号也没有**（QQ 不会自动把转发里的视频下到 `nt_data`）。
4. bot 看到本地路径后只走复制，**不再走 HTTP**；转发拆包又带了 `skip_url_refresh=True`，连 `get_file` 都不试。

对照同一晚 20:13:58 主号 **直接发** 到群里的视频：NapCat 给出了 `https://multimedia.nt.qq.com.cn/download?appid=1415&...`，bot 直连 CDN 成功。差别只在「群内真实视频消息」vs「嵌套转发里的私聊录像」。

### 5.3 熔断器

`xw("video-url-get", ...)` → `M0e.callResource`。失败计入 `failureCount`，超阈值后 `disableUntil = now + 30s`。20:18:39 时统计已是 `success: 9, failure: 47`。前 10 个视频每个都 NaN，后 1 个直接被熔断短路，全部落入 `a = e.filePath`。

## 6. Bot 侧把缺口放大了

`plugins/media_archiver/listener.py`：

1. **`get_msg` 解包路径写错**（约 1342 行）  
   `msg_resp.get("data", {}).get("message")`。NoneBot 的 `call_api` 已经返回 `data` 本体。这条路径从未命中，总是落到 `get_forward_msg`。对这次事故影响不大：两条 API 给出的视频 `url` 都是同一条本地路径。

2. **转发媒体 `skip_url_refresh=True`**（约 1314、1456 行）  
   本意是避免 `get_image` / `downloadMedia` 对转发消息超时。副作用：本地路径复制失败后，**禁止** `_try_get_file_download`。NapCat 其实把 `{peer, msgId, elementId, fileUUID}` 按文件名缓存在内存里（`Jt.encode`，TTL 24h），`get_file(file=文件名)` 理论上能触发 `downloadMedia`。转发场景下这个调用经常超时，所以被刻意关掉了。

3. **本地路径一旦出现就不走 HTTP**（约 325–349 行）  
   `_is_local_path` 为真 → 只复制。没有「路径不存在则回头用 fileUuid 换 CDN」的分支。而 OneBot 视频段里已经没有 fileUuid 了，bot 单凭这段 JSON 也拼不出 `multimedia.nt.qq.com.cn` 链接。

4. **跨账号复制只能救「主号本地已经有文件」的情况**  
   20:16:41 那条转发（`1741796593`）也是同样的 NapCat URL 失败，但文件在 `512239520\Video\2026-09\Ori\` 里，复制成功。20:18:39 这批 `2026-08` 视频主号缓存对不上 hash，这条退路也没了。

## 8. 根因归纳

| 层级 | 现象 | 是否本事故主因 |
|---|---|---|
| NapCat `getVideoUrlPacket` | 内层 private 的 `peerUid`（UID 字符串）被 `+` 成 NaN，当作群号写入 protobuf | **是** |
| NapCat `videoElement` 失败回退 | 用 `filePath` 冒充 `url`，bot 无法区分「有缓存」和「只有路径字符串」 | **是** |
| QQ NT | 转发视频不会自动下载到接收号 `Video\Ori` | 是（前置条件） |
| NapCat 熔断 `video-url-get` | 放大：第 11 个视频连试都不试 | 次要 |
| bot `skip_url_refresh` | 关掉 get_file / CDN 二次尝试 | 次要（放大） |
| bot `get_msg` 看错 `data` | 多打一次 `get_forward_msg`，不改变视频 URL | 否 |
| HTTP 下载器 | 未被调用 | 否 |

一句话：**嵌套转发里的视频被 NapCat 当成「群视频 + 私聊 peerUid」去组 OIDB 包，组包阶段就 NaN；然后把不存在的本地路径交给 bot，bot 只复制不下载。**

## 9. 修复建议（未实施，供选择）

### A. 修 NapCat（治本，但要改 `napcat.mjs` 或等上游）

`getVideoUrlPacket` 里：

- `+e` 之前判断 `e` 是否纯数字。
- 非数字 / 空：不要走 `GetGroupVideoUrl`，改走 `GetVideoUrl(e, node)`（C2C，`targetUid` 是 string）。
- 若内层是转发：用 `parentMsgPeer.peerUid`（这次外层是 `663964060`）当群号，而不是内层 private 的 UID。
- `videoElement` 失败时不要把不存在的 `filePath` 填进 `url`；留空或另给 `path` 字段，让 bot 知道「没 URL」。

这是上游逻辑问题。硬改本地 minify 后的 `napcat.mjs` 可验证，但升级 NapCat 会被覆盖。

### B. 修 bot（治标，可落地）

1. 本地路径复制失败后，**即使是转发**也试一次 `get_file(file=文件名)`。NapCat 内存里还缓存着 fileUuid（24h）。要接受可能超时。
2. 区分「路径存在」和「路径字符串」：不存在就不要当下载成功条件结束。
3. 修 `get_msg` 的 `data` 解包（顺手，不解决视频 URL）。
4. 图片已经证明转发 CDN 可用；视频需要 NapCat 先把 URL 给出来，bot 无法从当前 OneBot 段还原 fileUuid。

建议优先 **B1 + 向上游反馈 A**。若只做 B1，对「fileUuid 还在 NapCat 内存、downloadMedia 能拉下来」的近期转发有效；对已经熔断、或内层 peer 完全无效的情况，仍可能超时失败。

### C. 不建议

- 打开 `parseMultMsg=true`：上报事件会变大，URL 生成走同一套 `videoElement`，一样 NaN。
- 只在主号缓存里盲搜：这次 11 个文件主号就没有。
